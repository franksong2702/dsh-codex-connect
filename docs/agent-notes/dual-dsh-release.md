# One plugin artifact for two DSH targets

Alpha 4.33 is prepared as one plugin release for DSH `0.1.2-rc.1` with pi-ai `^0.84.2` and DSH `0.1.5-alpha.1` with pi-ai `0.85.1`. The public compatibility record and installation recommendation are separate from these intended dependency targets and remain unchanged until release acceptance. The baseline `dshPluginApi.version` remains available to upstream discovery; its additive `versions` list names the exact declared installation targets. Package peers accept only those DSH versions, not an interval of untested releases. Runtime diagnostics reject mixed DSH package versions and mismatched DSH/pi-ai pairs.

The alpha dependency probe found that native pi-ai Astra metadata reintroduced Minimal, bypassing the plugin's calibrated five-level fallback. Native names, limits, and other metadata are retained while the same reasoning exclusions and upper levels apply to both sources. A synthetic native catalog reproduces the regression under the baseline dependencies as well. The image restoration fixture transfers detached snapshots through the public SessionStore preparation API with the ownership metadata accepted by each target; production session persistence remains upstream-owned. Vendored OAuth verification uses a separately pinned development alias for pi-ai `0.84.4`, independent of the runtime provider version; the vendored files, local security patches, and source-version rejection remain unchanged.

Both declared and undeclared installation checks use packed artifacts. The declared matrix requires every exact target, matching package versions and SHA-256 digests, unchanged host defaults, model reasoning metadata, and successful provider disposal. The weekly canary calls this matrix instead of its obsolete fixed host override. Future upstream discovery remains independent and does not certify a release.

Release evidence and remaining acceptance gates are tracked in the repository's `.github/ALPHA_433_RELEASE_READINESS.md`. Automated checks and existing-token requests do not substitute for fresh OAuth login, cancellation, or complete optional-capability acceptance. No existing profile, account setting, deployment, or release is changed by these checks.

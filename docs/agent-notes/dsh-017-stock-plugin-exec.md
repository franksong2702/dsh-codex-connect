# DSH 0.1.7-rc.1 stock plugin-exec compatibility

The stock `dsh plugin ... exec` launcher runs the installed plugin command in a separate Node process without DSH's process-local profile resolver. Codex Connect's previous `bin` output shared an eagerly imported chunk with its runtime entry, so even `doctor` failed during ESM linking on the first inaccessible host peer, `@deepseek-ai/schemastery`. The peer was present in the exact host; adding a package declaration, copying host packages into the profile, or retrying authentication would not repair that lookup. The earlier DSH alpha.2 local launcher patch used a fallback operation removed by rc.1, so this release does not depend on that patch or an upstream change.

The command entry is now built separately and carries the libraries it needs in its own CLI output. The runtime entry still imports host peers externally, retaining Cordis and service identity. `doctor --install-anchor` reads version metadata relative to an explicitly named DSH `package.json` without loading host modules or returning the path; absent an anchor and visible peer metadata it reports `unknown`, not a false compatibility verdict. The isolated checker passes the exact host anchor to `doctor` and initializes DSH's own `PluginPackages` resolver before importing the installed runtime plugin. Neither checker creates manual peer links.

Standalone diagnostics read the Codex model catalog without importing the runtime adapter. That keeps DSH's other model adapters and pi-ai's unrelated provider loaders out of the published CLI; the package check rejects their generated chunks. The remaining CodeQL password-hash alert also existed on `main` as alert #23: Reserve hashes an account/user identity pair for a private return-target match, not a password or credential verifier. It cannot authorize a backend request without the freshly captured OAuth token and server response. Alert #23 was dismissed as a false positive with this specific rationale; security scanning remains enabled.

The exact stock DSH `0.1.7-rc.1` installation passed the Node 22 matrix using one packed plugin artifact. It verified ten prepared models, unchanged defaults, provider disposal, synthetic Reserve transitions, ten distinct native-compaction process phases across none/zstd, and synthetic image generation/download visibility; no real OAuth or provider request was made. The Node 22 complete source check passed 116 files and 1,307 tests; Chromium passed 60 tests. The source check under default Node 26 initially failed because that version rejects a probe's `--experimental-transform-types` option, while its sandboxed socket failures were caused by `listen EPERM`; the supported Node 22 host-permission run passed. The replacement installed Session gate targets rc.1 and verifies that the stock page shows the ordinary Composer without Task controls and that the signed Task route rejects activation. It does not claim migration of old Task grants across a Harness upgrade, real-account acceptance, merge, publication, or deployment.

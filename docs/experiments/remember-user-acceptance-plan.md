## Proposed user scenario

Use a disposable conversation about preparing a small community-library activity. Establish three ordinary requirements: a maximum of 20 participants, an indoor venue, and no purchases of new equipment. Discuss two alternatives and explicitly reject one of them. Ask the assistant to keep an unfinished next action, such as comparing the two staffing arrangements.

The engineer, not the user, then performs and verifies manual compaction and a normal stop/reopen of the isolated process. Resume the same conversation. The next question should not repeat the earlier requirements or reveal the rejected alternative: ask the assistant to continue the unfinished comparison and give its recommendation with reasons.

The user judges whether the conversation still feels continuous: are the three requirements respected; is the rejected option kept rejected; does it continue the pending work without asking for facts already supplied? No special memory marker or internal terminology should be needed from the user.

## Evidence and interpretation

Separate engineering observations (exact source/session identity, actual compaction, persisted checkpoint, fresh process, new completed turn) from the user's product feedback. A plausible answer without verified compaction is not acceptance. A matching checkpoint without correct task continuation is not acceptance either.

Record only the specifically agreed synthetic-task results and concise feedback, never credentials, opaque checkpoint content or actual project conversations. One pass supports only this bounded experience. Broader quality, tools, images, forks, unexpected crashes, repeated compaction and Astra each need separately scoped evaluation.

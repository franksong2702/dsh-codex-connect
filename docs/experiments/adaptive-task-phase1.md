# Adaptive task Phase 1: user-granted model selection

Status: unpublished engineering candidate, based on M3 #234 at `535b8f5`. This is a different product flow from the older Astra-only, per-change Think confirmation experiment. The original M1/M2/M3 branches, their journal guards, published Alpha 4.39, and all existing defaults remain unchanged. It is not a live model/value acceptance or a release.

## What a user can actually do

Open **Model choice / 模型选择** in an empty, ordinary conversation and explicitly start with the displayed scope. The task starts with **Sol / Medium**; this is the agreed experimental baseline, not a measured optimal router. Follow-up messages in the same conversation remain in this task until the user takes over manually. No profile default is changed and another conversation receives no grant.

The initial scope permits the currently catalog-supported efforts for the selected Sol/Terra/Luna/Astra models. Advanced details allow excluding models and selecting a request ceiling (default 40, accepted range 1–200). These are experimental bounds, not empirically calibrated savings settings. The initial Sol route is required. Catalog capability is explicitly distinguished from the account's model eligibility: no live eligibility probe is made and a missing/unavailable route is never silently replaced.

Within that scope the current model can keep doing the work, change effort, or request another main model for the next request through `codex_connect_change_work_model`. It is not forced to use the tool, produce a routing report, choose a predetermined role or invoke a separate planner. A new main model has the same optional capability within the same grant. Subagent execution is not introduced in Phase 1: children of an active task cannot bypass its accounting through the ordinary adapter. No file, command, network-tool, publication, or review permission is granted by selecting a model. Existing host tool/sandbox approvals remain their owners.

The drawer distinguishes a requested next choice from the last **recorded** request; neither means the provider accepted a request or solved the task. It reads current host state on opening/focus, not a periodic background poll. Mutations carry an operation id and policy revision, are never automatically retried, and show uncertainty after a lost reply until the user rereads authoritative state. Reopening cannot briefly present actions based on an old snapshot. English and Chinese flows and phone-width rendering are exercised.

## Authority and accounting

The actual DSH Connection `requestRejection` and signed browser-cookie validation protect the exact GET/POST endpoint. Controls are bound to a hash of the exact verified browser credential and authority, and the exact live root Agent/session identity. This is not a named-user ACL: copied cookies are the same principal, a newly issued different cookie is a different principal, and cross-device/browser reauthorization recovery is not implemented. Raw cookies and OAuth data are never copied into the grant or returned in task responses. An installation without the Connection service exposes no unauthenticated substitute.

A private `codex-connect-tasks` directory next to the configured credential-store location holds strict, bounded task documents containing the grant, route, session fingerprint, request reservation count, runtime epoch and bounded operation receipts. No conversation text, rationale, tokens or credentials is placed in this store. This is task authority/accounting, not a second version of the Think effort journal. POSIX files/directories are 0600/0700; regular-file, size, symlink, hardlink and schema checks fail closed. The host atomic-write/lock primitive serializes updates across independent store objects; reservations are synced before fetch. Local host code and its authorized filesystem owner remain trusted; this is not an OS security sandbox against that owner.

Each actual managed backend attempt reserves against the same task before transport. Parent model requests, their existing compaction paths, and direct Codex auxiliary work correctly attributed by the host's live initiator share the counter. Requests inside queue/cooldown wait are not reserved until admission; cancellation or transport uncertainty after reservation never refunds the count. No new automatic model retry is introduced. Unattributed, unrelated profile/background activity is not guessed into a task and this does not meter arbitrary third-party traffic. Missing usage is not fabricated. This counter is **not** tokens, API price, a subscription quota estimate, or proof that cancellation instantly stopped server computation.

A standard host journal/inbox notice identifies that a task grant existed but is never interpreted as approval. If the state file disappears, the marker prevents silently treating a restored task as ordinary unbounded work. Unknown/corrupt state is not migrated into a fresh allowance. Restoring an active grant into a new runtime epoch changes it to interrupted; the same authorized browser must explicitly resume, with counters retained. A fork/new Agent cannot inherit or manufacture a grant by copying a message.

## Model changes, context and exit

A handoff here changes the next request of the **same host-owned main Agent/session**. It does not create another OS worker or secretly execute a second controller. Current user requirements, visible model findings and tool results remain in the original host journal. An ordinary request-level model/effort choice is used; Phase 1 does not generalize Astra's native `configuration_update` protocol to other models and does not remove the older replay guards.

For a changed route/effort, private assistant reasoning/replay metadata is omitted from the portable input, while visible text, tool calls/results and supported image references are retained. Foreign or pre-handoff compaction checkpoints are expanded only from their correlated original source records. New, correlated checkpoints made on the target model after handoff remain usable, so subsequent compaction can reduce context again. Unknown replacement history, missing records, unsupported content or transfers above 512,000 bytes are rejected rather than truncated or guessed. The normal host attachment resolver still controls whether a target actually supports an attachment. This is a bounded transfer protocol, not a claim of lossless compatibility with every model/native checkpoint.

Native host compaction intentionally may omit an effort. It remains host-owned, on the task's model and within catalog/grant facts; its actual HTTP attempts are counted without falsely treating a default compaction effort as a user-selected new task level. Phase 1 source tests exercise ordinary compaction/handoff composition; existing M1/M3 native-compaction regressions remain separate evidence, not proof of every new live combination.

Manual takeover revokes the tool, cancels in-flight automatic work, drops pending automatic choices and permits normal later model/Default selection using a safe portable projection. The user then controls future requests outside this ended automatic grant; the historical task counter is not a lifetime restriction on manual use. Stop cancels the host task and leaves it stopped, with a distinct stopping state until the host is idle. Runtime restart is not permission to resume. Declining to start requires no model question, and manual takeover cannot be reversed by a model. Existing Astra-only Think histories are not silently converted; Phase 1 starts in a new conversation with that legacy feature disabled. Its separate old-history exit limitation has not been relabeled as fixed by this entry.

## Verification and remaining gates

Run `pnpm run check`, `pnpm run test:browser`, `node scripts/check-adaptive-task-ui.mjs`, `node scripts/check-adaptive-task-persistence.mjs`, `node scripts/check-think-matrix.mjs`, and `pnpm run check:dsh-matrix`. The exact-host contract now requires all 25 task cases as well as existing Think/M2/M3 cases and runtime identity; old matrix reports do not satisfy it. Task authorization, request reservations, cold-process replacement, original requirements, state loss, manual exit, stale operations and actual cookie-authenticated controls have separate checks.

The Chromium integration uses the actual control, actual signed-cookie DSH authentication and actual product endpoint/Agent/adapter. Its enclosing page/form is an isolated fixture, **not** full daily Gateway/profile/Session-page human acceptance. All provider replies and credentials are synthetic. Neither fixture routing choices nor passing tests establish which model should do a real task. The comparison plan in `adaptive-task-evaluation.md` is deliberately unexecuted until separate live-account/task/usage authorization. Independent source review, full installed user acceptance, account eligibility and real economic benefit remain unclaimed. No merge, publication, deployment, daily-service restart or automatic user enablement is included.

# Experimental Astra reasoning changes

This experiment is available only in the reviewed PR #167 build, not published Alpha 4.33. Use an isolated test profile with DSH `0.1.2-rc.1` / pi-ai `0.84.4` or DSH `0.1.5-alpha.1` / pi-ai `0.85.1`; do not mix the host package versions. The PR identifies the exact install commit and its validation results.

This feature is default-off and intended for testing. It uses Astra `configuration_update` input items to change effort for later requests without changing the original request-level effort. Cache reuse, output quality, subscription usage, and account availability are not guaranteed.

## Try it

1. Install the PR build in a test DSH profile. This PR is not an npm release; keep the normal profile unchanged.
2. In Settings → Plugins → Plugin configuration → Codex Connect, enable **Experimental Astra reasoning changes** and save. The corresponding plugin config is `enableReasoningUpdates: true`.
3. Start a new GPT-6 Astra conversation and explicitly choose `low`, `medium`, `high`, `xhigh`, or `max`; do not use Default.
4. Discuss an ordinary requirement, then progress naturally into a difficult design or diagnosis and finally routine wrap-up. Do not mention reasoning levels or name the tool: the model receives the proactive recommendation guidance itself.
5. Observe whether Astra proposes a justified change at a useful moment, avoids repetitive questions, and respects refusal. Approve or decline a proposal through the native question. A change is not mandatory: retaining the current level can be appropriate. Judge the recommendation, not the number of calls.
6. After approval, continue the task and later resume the same conversation. The tool reports a queued change; the approved notice enters the next request after its configuration update. When DSH records that request, the model selector displays the effective level, such as High, without a separate initial-level label. The original wire-level effort stays internal to the plugin. Request evidence is needed to verify actual wire effort; UI behavior alone does not establish service-side execution.

Developer-only smoke tests may explicitly request `codex_connect_set_reasoning_effort`. They verify the confirmation/replay plumbing, not autonomous recommendation quality, and are not the main user acceptance test.

Astra assesses the next phase's unresolved questions and failure cost at meaningful task transitions. Uncertain causes, competing designs, consequential decisions, or evidence invalidating a plan can justify an increase. Once the cause, approach, scope, and acceptance criteria are clear, it explicitly considers a decrease for bounded implementation, routine verification, or follow-up. A written plan is not itself a downgrade trigger: concurrency, security, or migration work may still be difficult. No phase has a mandatory level. Keeping the current level means continuing without another question; tool calls alone do not trigger reassessment, and refusal or manual choice is not reopened without materially changed work or evidence. Proposals briefly identify the upcoming work, what changed, and why the requested level fits. The objective includes reliable completion, rework, and user time, with no quality or quota-saving promise. Harness does not score difficulty or decide a level; tool proposals still require human confirmation and explicit manual choices take priority.

A logged state notice supplies the original and effective effort and a short reminder of this policy on initial admission and when the notice changes. The full policy lives in the tool description. Restored history retains notices; identical notices are not repeatedly appended. Default is reported as lacking an explicit initial selection, not guessed. Keyless request snapshots verify delivery of the policy, not the model's judgment or actual savings.

Declining makes no change. Canceling before admission can discard the queued notice. Disabling the option removes new proposals and cancels pending questions; already admitted approvals continue to replay. It does not reset an existing conversation's effective effort. To reset without another confirmed update, start a new conversation.

## Limits and verification

The initial version supports only the live main agent, the original session identity, full uncompacted history, and an unchanged provider/model. With the feature enabled, an explicit Astra effort chosen in the native selector is recorded as an update on the next step; the latest choice wins, including a return to the original level. It does not require another tool question. A selection changed after step admission is rejected before dispatch and can be applied on retry. Default and provider/model switches remain unsupported. Forks containing approvals, compaction, auxiliary model calls, automatic truncation, and server-side previous-response chaining are rejected. Start a new conversation when one of these is needed. A profile must supply a human-question answerer.

Keyless tests assemble the real DSH agent loop, model-selection hooks, tool runtime, user-question service, Codex adapter, and synthetic SSE transport on both supported host versions. They cover approval/decline, cancellation/unload, disabling during confirmation, replay with proposals disabled, concurrent manual selections, successive upgrades and downgrades, persisted session JSON restoration, original-position replay, unchanged defaults, and default-off installation. A jsdom test loads the installed DSH client bundle and verifies the real ModelDirectory and Composer render changing projection values and retain the effective label on remount; decorative icons and toast are stubbed. Chromium tests cover staging, discarding, saving, remounting and disabling the settings switch in both languages. These tests do not establish live ChatGPT acceptance or a complete deployed DSH interaction; those remain the user test.

## Implementation note

Approval is stored in the ordinary `user/message` event as structured `dsh-codex-connect` plugin-source metadata, together with its visible notice. No text pattern grants approval, no defaults are written, and no mutable per-session override table is used. DSH's session append/restore validation preserves the metadata. The provider's public payload hook inserts updates using request-local asynchronous scope after the normal pi-ai conversion, including prepared calls. Guards reject missing or inconsistent approvals before dispatch.

The public `agent/request` waterfall returns the confirmed effective effort after the normal model-selection hooks resolve. DSH records it in `request/header`; its existing model-selection projection updates Composer and survives refresh or restoration. Before admission or request preparation completes, no new header is written. A later transport failure does not undo an already recorded request configuration; the selector reports configured effort, not successful remote execution. The plugin does not call `selectModel`, because that operation also saves the default selection. Old sessions whose headers still contain the initial effort synchronize on their next request, not merely by opening the history. At the provider payload hook, the first approved notice supplies the immutable original wire effort and each update retains its original input position. This separates DSH's current selection from the historical wire base without changing Harness or pi-ai.

DSH `0.1.5-alpha.1` prepares configuration before admitting the proposed user batch; `0.1.2-rc.1` admits it first. The guard retains only the current proposed batch per live agent, matched by turn, step and cancellation signal. Already admitted messages are not duplicated. Canceled batches are ignored; the next proposal, terminal error or turn stop replaces or removes the reference. This transient batch is not an effort override: the provider still validates admitted structured approvals before dispatch, and restored state comes only from the session log.

The newer host adapter also moves a leading system message into the provider system prompt. The conversion hook shifts approval positions only when the actual converted context has exactly one fewer user message and the same leading prompt. Legacy in-history prompts and explicit system overrides retain their positions. Unexplained message-count changes, mismatched prompts, removed approvals and reordered notices remain errors; no upstream converter or SSE parser is replaced.

The protocol reference is [OpenAI: Change reasoning mid-conversation](https://developers.openai.com/api/docs/guides/reasoning#change-reasoning-mid-conversation). This plugin intentionally supports a smaller subset than the protocol: in particular, it does not implement compaction-trigger reinsertion.

Manual selection repair: a logged `model/selection` is explicit host selection intent, not an unconfirmed model proposal. The plugin admits a structured update and links its source metadata to that selection's sequence number, so an unchanged request header or a later tool approval cannot reapply the old selection. Legacy sessions with a High approval followed by Medium then Low continue at Low instead of failing; choosing High continues at High. The plugin itself never saves defaults; the native selector retains Harness's existing default-saving behavior. Regression tests restore synthetic legacy histories, replay manual Low/Medium/Max followed by successive confirmed changes, and reject late concurrent changes. No private user conversation is stored in the fixtures.

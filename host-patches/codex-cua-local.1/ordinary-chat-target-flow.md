# Ordinary conversation preparation — local.6 source checkpoint

This candidate is unpublished, default-off and not deployed. It changes the preparation and consent sequence, not the persistent permission store. It is not live Computer Use acceptance or a native-performance comparison.

## Implemented sequence

1. The ordinary parent model calls `codex_computer_use({goal})`. The companion checks the exact live root object, official provider, capability identity and exclusive task lease. The parent model remains unchanged.
2. `cuaTaskApproval` version 2 `prepare({parent, goal, signal, expiresAt})` reads only the latest admitted human message. The model's goal does not authorize which application to enumerate. Preparation freezes the admitted input ID, exact goal and expiry; claim/begin verify that same immutable intent. Host-private `listApps` metadata is filtered by the named related application; only related instances receive retained native handles and bounded window-metadata reads.
3. A unique window is prepared automatically. Ambiguity or a missing application name is resolved through the same root's blocking human-question service. The directory and candidate labels never become tool results, system text, session messages or child input. No page AX tree, screenshot or input is admitted here.
4. A real owned Terra/high child is created. Before its first model request, a Host-owned `getApp` call goes through that child's standard Native executor and the existing single-task permission pipeline. The actual root human must approve the exact application/window/task/expiry. Offline tests script an answerer; production does not.
5. Only after approval does the child receive the goal and selected target. Existing native strict-window/snapshot checks apply to observation, click, form value and scroll. Completion/Stop/refusal/expiry invalidate the in-memory task and drain the private native channel. Refusal and cancellation lock the admitted input against automatic re-prompting. A different admitted or queued human input in that exact root closes both metadata preparation and pending/active consent; a late answer cannot revive the old task.

Exact fixed-target configurations and the old operator RPC remain legacy/recovery paths. Ordinary use with empty application/window configuration has no settings-page prerequisite. Unknown, stale or cleanup-uncertain legacy selections remain blocked.

## Verification boundaries

The normal-chat integration uses the real Host Agent loop, native executor, root question service and permission code, with in-memory Flash/Terra responses and a synthetic native transport. It verifies request ordering, parent model preservation, ambiguity, denial, Stop, refusal reuse, no persistent grants and candidate privacy. It does not execute the native helper, contact a model or operate a desktop.

The unit-tested preparation module is embedded verbatim in the Host patch; a regression asserts the embedding. The exact official package lock and complete-file verification remain in force. A new native window-metadata query invalidates anchors only for the same process identity, so other related instances' retained candidates survive until selection. Final binding and all old process/window identity checks remain required.

## Remaining window input work

This checkpoint deliberately does not admit `pressKey` or `typeText`: the published keyboard sink targets a PID, and its per-event check is cancellation only. Giving those methods a `windowId` in a model guard would not establish a native window boundary.

The next bounded interface must be distinct from raw app-wide input: a retained process/window anchor, exact focused-window and focused-element ownership check immediately before every key-down/text scalar, repeated identity/cancellation checks, and release-only key-up cleanup if focus or Stop changes. Chords that create/close resources, app switching and clipboard access must stay denied. A browser navigation transaction additionally needs a verified browser/address-field binding and strict HTTP/HTTPS URL parsing; unrestricted address-bar text plus Return would defeat a navigation scheme policy. These constraints must be implemented and tested at the native sink and Host dispatch, then independently reviewed. Current code does not claim these contracts exist.

Starting an application, creating a window/tab and cross-application tasks require their own resource identity, scope and concrete human consent. They are design-only under this admission. No daily-service deployment or GUI/model request is authorized by this source checkpoint; later acceptance still requires a reviewed exact candidate and real human task approval.

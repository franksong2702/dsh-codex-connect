# Experimental Terra Computer Use companion

This explicit, default-off companion exposes `codex_computer_use({ goal })`. It creates a fresh owned `openai-codex / gpt-6.1-terra / high` Agent through the published DSH factory. The parent model and session are unchanged. It is separate from frozen Adaptive Task and does not install a background task service.

The distinctly versioned local `0.2.2-alpha.2.codex-cua-local.7` combines task consent, private ordinary-chat target preparation and bounded Chrome-instance input. Exact published `0.2.2-alpha.2` and local.1 sets remain recognized for diagnostics, but a missing live `cuaTaskApproval` capability returns blocked before any child model request. Mixed versions are refused. Codex Connect's separate exact compatibility gate must also pass before installation. This package is private and experimental, not a release.

The existing public DSH macOS CUA provider must be configured with `agentPreset: codex-terra-computer-use` for the empty dedicated preset. DSH admits only one provider; this companion never creates a second one. The child selects `NativeToolExecutor` and uses the standard Host pipeline. Its guard admits only CUA and a terminal report, with one identity-bound application and window. The new local.6 flow prepares that target privately inside the Host from the admitted human message.

Published Host window snapshots include application-global AX roots and actionable menu elements. Stock Host therefore retains the defensive screenshot/coordinate-click/scroll route, with AX/form input blocked. The local candidate adds a live `cuaWindowScope` version 1 contract and native per-element window checks. Only when configured `strictWindowScope:true` does the worker admit `getState` in the configured window, and only its latest `windowScope:strict-window` snapshot can admit element click or `setValue`. Missing/foreign attestation or provider unload stops the worker. Raw `pressKey`/`typeText`, clipboard, model desktop discovery, secondary actions, menus, shell, PTC, file/network tools and further delegation remain unavailable. Local.7 adds a separate consent-bound `taskInput` contract for the selected Chrome instance, described below. The native Host independently enforces ownership at the mutation sink. These source/fixture results do not establish real AX acceptance; deployment still requires review, full compatibility checks and rollback.

Local.6 removes the configuration-page selection prerequisite for ordinary conversation tasks. With empty `application` and zero `windowId`, the companion calls the Host's version-2 preparation contract with the exact live root object. Only admitted human input supplies the application scope; a model-written goal or session identifier cannot grant discovery. The Host filters the running-application directory privately, binds a unique related window automatically, or asks the human to resolve ambiguity in that same root conversation. Candidate labels and the unrelated application directory do not enter parent or worker model messages. If no already-open application matches, a human clarification is required; app launch and creating another window are outside this contract.

Preparation grants no control. Before the first Terra request, a real owned child uses the standard Native tool pipeline to request task consent in its genuine root conversation, displaying the chosen application/window, goal and expiration. Chrome-instance input shows **允许这一次** / **拒绝**, with the instance scope and window-switch risk in plain language; legacy window-only tasks retain **Allow this task** / **Deny**. Only a real human answer admits page observation or input. Stop, refusal, expiration, changed admitted input, lost identity and uncertain cleanup fail closed. Refusal or cancellation requires new human input. No permission is copied from the root or written to the persistent application store. A previous operator-prepared target or explicit fixed-target configuration remains a legacy path, not an ordinary-use requirement.

Local.7 admits one separate `taskInput` operation only after actual human consent for the selected, retained `com.google.Chrome` instance. Its kinds are `text` (1–256 Unicode scalars), one bounded `key` chord, and `navigate` (a bounded HTTP/HTTPS address). The ordinary conversation needs no PID, settings-page preselection or pre-opened destination. The Host initially focuses the retained window after approval, arms once, and never automatically refocuses after takeover. The child receives no private arming/check interface. Existing click, form-value, observation and scroll capabilities retain the original strict-window contract.

Keyboard delivery is scoped to the application instance, not atomically isolated to one window. Each event checks the retained process/start identity, pinned executable file, focused AX window, expiry, cancellation and hardware event counters. The Host also checks between worker steps and monitors an idle/in-flight task every 200 ms through the same serialized native channel. A detected change permanently closes this task; it requires new human input before another task. This is sampled detection, not a guarantee that every transient switch between samples is seen. An in-flight key or cleanup release may still land in another window of the approved Chrome instance. The task card explains this residual risk. Counters record no keys, pointer positions or page content, and no event tap or new OS permission is requested.

Only editing/navigation chords are admitted; clipboard, app/window creation, app switching, system shortcuts, key holds and arbitrary chord sequences are rejected. The dedicated navigation entry accepts bounded HTTP/HTTPS URLs without credentials and rejects `javascript:`, `file:` and external-app schemes before input. It dispatches the browser address chord, text and Return under per-event checks. A dispatch requires a new observation before completion. This URL policy is not a sandbox around everything the browser UI or generic typing can do. No new application, new window, cross-application resources or persistent access is admitted.

This is an unpublished source candidate. Real Chrome delivery, hardware-counter behavior, human consent and effective backend identity still require separately authorized acceptance. Synthetic fixtures and compilation cannot establish live usability or performance parity. The running daily instance is not updated by this source checkpoint.

A per-user exclusive desktop file lease is held until the child and native work drain. Cancellation, deadline, operation/step budgets, parent disposal and lease loss close execution. Uncertain cleanup retains the lease for operator recovery. This coordinates instances of this companion only; it cannot lock out humans or unrelated automation. Native cancellation is cooperative; an unresponsive Host can delay quiescence past the requested deadline. It must never be reported as completed merely because the timer expired.

Native batches execute with concurrency one. A synchronous scoped `tools/result` observer commits authorization, snapshot identity and observation state before the next call reaches its guard. A refusal stops later input, while form values and a click can share a model step. Non-left buttons, modifiers and holds remain denied. Click/scroll/setValue invalidates completion evidence until a fresh successful observation. These restrictions prevent explicit indexed/context-menu routes; they cannot guarantee an application never opens a menu as an ordinary left-click effect. No live menu or desktop boundary acceptance has occurred.

The result includes structured status, finite reason, requested route and prepared Host request-header route, child session identity, model step/CUA counts and elapsed time. The backend's actual effective model remains unknown; a prepared Host route is not a server attestation. `completed` means worker-reported completion following an observation. It is not independent acceptance, a billed-cost measurement, or proof of parity with native Codex. Real provider and GUI performance acceptance remain outstanding. Host cancellation may replace the tool body outcome with its canonical structured `ABORTED` error; the bridge does not override that policy to fabricate a successful result.

## Validation

`test/host.test.mjs` runs against the actual published Agent loop, preset registry and Native tool pipeline with an in-memory scripted provider and synthetic CUA channel. It never makes a model request, opens an application, captures a screenshot, or creates credentials. The official CUA authorization case uses `installCua` with a synthetic transport, not a reimplementation of its consent policy.

Run the tests from a copy of this package below an isolated exact-version Host fixture. ESM resolves peers from that fixture; running directly in the parent repository would incorrectly resolve its older baseline Host. The checked-in Host checker prepares this fixture and tests the copied package bytes. Do not point it at a daily profile.

For local acceptance, first validate the Connect/Host combination, obtain review of the exact candidate and verify rollback. Then an operator may enable the companion in the target profile, resolve any new system/application consent themselves, and ask any parent model to call `codex_computer_use`. Live requests consume the user's subscription allowance. The prepared five-task native pilot is observational only; its effective model/effort is unknown. Custom live runs and a comparable native route/identity are still required before a performance comparison.
